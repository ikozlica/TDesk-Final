# Functional Requirements Document (FRD) — TDesk2

> Единая терминология: Client, Order, Invoice, Payment, Payout, User, Role, Audit Event.
> MVP не включает mailbox/email threads/встроенную переписку.

## 1) Dashboard
- Назначение: дать моментальную операционную и финансовую картину.
- Ключевые действия пользователя:
  - Просмотр KPI по заказам, счетам, выплатам.
  - Просмотр алертов по просрочкам и блокирующим состояниям.
- Валидации:
  - Фильтры по датам/статусам должны быть корректны и существовать в справочниках.
- Ошибки/edge-cases:
  - Нет данных за период → показывать empty state, не ошибку.
- Acceptance criteria:
  - Пользователь с правом view_dashboard видит актуальные агрегаты < 5 сек.
- MVP: базовые виджеты и фильтры.
- Phase 2: кастомные виджеты и персонализация.

## 2) Clients
- Назначение: управление клиентской базой и статусами клиентов.
- Ключевые действия пользователя:
  - Создать/редактировать клиента.
  - Просматривать связанные заказы и счета.
- Валидации:
  - Уникальность клиентского идентификатора.
  - Обязательные поля: наименование, статус, основной контакт.
- Ошибки/edge-cases:
  - Дубликаты клиента с похожими реквизитами.
- Acceptance criteria:
  - Нельзя создать клиента без обязательных полей.
  - Из карточки клиента доступны связанные сущности.
- MVP: CRUD + базовые связи.
- Phase 2: дедупликация и скоринг качества данных.

## 3) Orders
- Назначение: управление жизненным циклом заказа.
- Ключевые действия пользователя:
  - Создание заказа из клиента.
  - Смена статусов и назначение ответственных.
- Валидации:
  - Заказ должен иметь клиента, дату, сумму и статус.
  - Переходы статусов только по DOMAIN_RULES.
- Ошибки/edge-cases:
  - Попытка перевода в Completed при незакрытых обязательствах.
- Acceptance criteria:
  - История статусов фиксируется audit-событиями.
  - Невалидные переходы блокируются.
- MVP: базовый workflow заказа.
- Phase 2: сложные многоветвевые workflows.

## 4) Invoices
- Назначение: выставление и контроль счетов.
- Ключевые действия пользователя:
  - Создать счёт по заказу.
  - Обновить статус (Draft/Issued/Paid/Overdue/Cancelled).
- Валидации:
  - Сумма счёта не должна превышать разрешённый лимит по заказу (если применимо).
  - Валюта и налоговые поля валидны.
- Ошибки/edge-cases:
  - Частичная оплата, повторная загрузка подтверждения оплаты.
- Acceptance criteria:
  - Оплаченный счёт не может быть изменён без спец. прав.
- MVP: lifecycle + связь с оплатами.
- Phase 2: пакетная генерация и advanced billing.

## 5) Offers
- Назначение: подготовка коммерческих предложений.
- Ключевые действия пользователя:
  - Создать оффер из шаблона.
  - Зафиксировать статус оффера.
- Валидации:
  - Обязательны клиент, срок действия, сумма/условия.
- Ошибки/edge-cases:
  - Истёкший оффер пытаются конвертировать в заказ.
- Acceptance criteria:
  - Оффер с истёкшим сроком не конвертируется без подтверждения.
- MVP: базовый учёт офферов.
- Phase 2: согласование и versioning.

## 6) Personnel
- Назначение: учёт сотрудников/исполнителей и назначений.
- Ключевые действия пользователя:
  - Ведение профиля персонала.
  - Назначение на заказ/задачу.
- Валидации:
  - Нельзя назначить неактивного сотрудника.
- Ошибки/edge-cases:
  - Конфликт назначения в календаре.
- Acceptance criteria:
  - Конфликты отображаются до сохранения назначения.
- MVP: базовый реестр и назначения.
- Phase 2: нагрузка, компетенции, прогнозирование.

## 7) Payouts
- Назначение: управление выплатами исполнителям.
- Ключевые действия пользователя:
  - Создать выплату.
  - Перевести по статусам до выполнения.
- Валидации:
  - Выплата должна ссылаться на основание (заказ/период/акт).
- Ошибки/edge-cases:
  - Повторная выплата по одному и тому же основанию.
- Acceptance criteria:
  - Дубликаты выплат блокируются правилом уникальности.
- MVP: payout lifecycle foundation.
- Phase 2: массовые выплаты и авто-сверка.

## 8) Finance
- Назначение: контроль обязательств, оплат, выплат и баланса.
- Ключевые действия пользователя:
  - Просмотр финансовых сводок.
  - Ручная сверка расхождений.
- Валидации:
  - Суммы операций должны быть консистентны с документами-основаниями.
- Ошибки/edge-cases:
  - Расхождения курсов/округлений.
- Acceptance criteria:
  - Все расхождения журналируются и имеют статус обработки.
- MVP: сводки и ручная сверка.
- Phase 2: расширенная аналитика и прогноз.

## 9) Calendar
- Назначение: планирование событий и дедлайнов.
- Ключевые действия пользователя:
  - Создать событие/дедлайн по заказу/счёту.
  - Фильтровать события по ответственным.
- Валидации:
  - Дата окончания не раньше даты начала.
- Ошибки/edge-cases:
  - Пересечение событий с критичной загрузкой.
- Acceptance criteria:
  - Критичные дедлайны подсвечиваются и отражаются в Dashboard.
- MVP: базовый календарь событий.
- Phase 2: синхронизация с внешними календарями.

## 10) Files
- Назначение: прикрепление и хранение файлов доменных сущностей.
- Ключевые действия пользователя:
  - Загрузить, скачать, удалить файл (по правам).
- Валидации:
  - Ограничение размера/типа файлов.
- Ошибки/edge-cases:
  - Повторная загрузка одинакового файла.
- Acceptance criteria:
  - Все действия с файлами аудируются.
- MVP: файловые вложения к сущностям.
- Phase 2: versioning и предпросмотр.

## 11) Templates
- Назначение: управление шаблонами документов/текстов.
- Ключевые действия пользователя:
  - Создание/редактирование шаблона.
  - Использование шаблона при формировании оффера/счёта.
- Валидации:
  - Шаблон должен проходить проверку placeholders.
- Ошибки/edge-cases:
  - Отсутствующий placeholder в контексте документа.
- Acceptance criteria:
  - Невалидный шаблон не допускается к публикации.
- MVP: базовые шаблоны и placeholders.
- Phase 2: версии, approval и A/B варианты.

## 12) References
- Назначение: централизованные справочники (статусы, типы, валюты и т.д.).
- Ключевые действия пользователя:
  - Управление значениями справочников (по правам).
- Валидации:
  - Нельзя удалить значение, которое используется активными сущностями.
- Ошибки/edge-cases:
  - Деактивация значения ломает существующий workflow.
- Acceptance criteria:
  - Используемые значения могут быть только деактивированы, не удалены.
- MVP: основные справочники.
- Phase 2: локализация и import/export.

## 13) Settings
- Назначение: системные параметры платформы.
- Ключевые действия пользователя:
  - Изменение конфигурации (валюта по умолчанию, timezone, policy-флаги).
- Валидации:
  - Изменения критичных настроек требуют повышенной роли.
- Ошибки/edge-cases:
  - Неконсистентные значения параметров.
- Acceptance criteria:
  - Все изменения settings логируются в Audit.
- MVP: ограниченный набор безопасных параметров.
- Phase 2: расширенная конфигурация с rollout-правилами.

## 14) Users / RBAC
- Назначение: управление пользователями, ролями и доступом.
- Ключевые действия пользователя:
  - Создать пользователя, назначить роли, деактивировать доступ.
- Валидации:
  - У пользователя минимум одна роль.
- Ошибки/edge-cases:
  - Потеря последнего Admin в системе.
- Acceptance criteria:
  - Система не допускает удаление/деактивацию последнего активного Admin.
- MVP: роли Admin/Manager/Finance/Readonly.
- Phase 2: Contractor + более гранулярные permissions.

## 15) Audit
- Назначение: трассируемость действий пользователей.
- Ключевые действия пользователя:
  - Просмотр журнала аудита по фильтрам.
- Валидации:
  - Нельзя редактировать или удалять audit entries.
- Ошибки/edge-cases:
  - Большой объём событий при пиковых нагрузках.
- Acceptance criteria:
  - Все критичные операции имеют неизменяемый audit event.
- MVP: базовый read-only журнал.
- Phase 2: расширенные отчёты и экспорт.

## Архитектурные ограничения для всех модулей
- UI не обращается напрямую в БД.
- UI не содержит бизнес-логики.
- Бизнес-правила реализуются в domain/application.
